# 운영 런북 (행사 당일 장애 대응)

부스 진행자가 노트북 앞에서 바로 참고할 수 있도록, 흔히 발생할 수 있는 문제와 대처법을 정리한다.

## ⚠️ 행사 전 필수 체크리스트 (2026-11-14 전에 반드시 확인)

- 🟠 **각자 테스팅(11/12까지)** — 모여서 하는 리허설은 없다(10/23 Bumm님). 노트북을 맡는 사람마다 [`../manual/self-test.md`](../manual/self-test.md) 한 장대로
  카메라 허용 · 와이파이 · 실제 생성 1건 · 프린터 4×6 인쇄를 해 보고 결과(특히 1장 인쇄 시간)를 담당자에게 보낸다.
- 🟠 **교육청 노트북 설치판 확인(11/12)** — 노트북마다 «스마트 앱 컨트롤»이 켜져 있는지(Windows 보안 › 앱 및 브라우저 컨트롤), 설치를 막는 관리 정책이 있는지,
  백신이 설치 파일을 격리하는지 본다. 끄거나 우회하지 않고 결과만 담당자에게 알린다(10/27 Bumm님 A안 — 설치 파일은 EXE 그대로).
### ① OpenAI 지출 한도와 이용 등급을 확인한다

- 🟢 **강제 한도 $250으로 설정됨**(2026-10-05 Bumm님 설정 확인 — 화면 문구 "Requests will start to fail
  when limit is reached", 조직 단위). 지출 **알림은 $10 단위로 $250까지** Bumm님이 직접 둔다.
  자동 충전은 잔액 $5일 때 $10, 월 $50까지.
- 🔴 **이용 등급(Usage tier)을 행사 전에 2단계 이상으로 올린다.** 2026-10-05 현재 **1단계**다. OpenAI 공식 표 기준
  1단계는 **월 사용 한도 $100**(위 $250 설정과 별개로 OpenAI가 거는 상한)이고, 이 앱의 모델(`gpt-image-2`)은
  **분당 이미지 5장**까지다. 행사 하루 예상 생성량(약 $100 안팎)이 이 상한에 닿을 수 있고, 노트북 4대가 동시에
  돌면 순간적으로 분당 5장을 넘겨 대기가 생긴다.
  - 2단계 조건: **누적 결제 $50** → 월 한도 $500, 분당 20장. 3단계는 누적 $100.
  - 어디서: platform.openai.com → 설정 → Limits에서 현재 등급 확인. 등급은 누적 결제액에 따라 자동으로 오른다.
- 1장당 약 $0.05다(2026-10-26 실측 $0.049~0.050). 한도에 닿으면 그 순간부터 부스 전체의 AI 생성이 멈춘다(화면은 «지금은 만들 수 없어요»를 보인다 — 대체 그림 인쇄 길은 2026-10-16에 없앴다).

### ② 노트북을 공인 IP에 고르게 붙인다

- **노트북 6대 = 가동 4대 + 항시 대기 2대, 공인 IP 3개**(2026-09-11 대표·현장 확정) —
  대략 **IP당 2대**다.
- 왜 고르게: `IP_RATE_LIMIT_MAX=50`(전역 150 ÷ IP 3개)이라, **한 IP에 몰리면 그 그룹만
  정상 사용으로도 50건에 먼저 닿아** 불필요한 429가 난다.
- 현장에서: 어느 노트북이 어느 와이파이를 쓰는지 확인해 대체로 나뉘어 있으면 된다.
- 🟢 실사용 부하는 이 한도 근처에 못 간다 — **프린터가 상한을 정해** 최악에도 IP 한도의 13%다
  ([`printer-capacity.md`](printer-capacity.md)). 이 항목은 "몰리면 억울한 429"를 막는 것이지
  한도가 모자라서 하는 것이 아니다.
- ⚠ 예전 문서에 있던 **"노트북 20대를 7/7/6으로"는 배치 계획이 아니었고**, 그 숫자 자체가
  2026-09-11에 폐기됐다(부하 테스트 목표치였는데 부하테스트를 안 하기로 했다). **실제 배치는 위 6대다.**

## 1. "AI 서버 연결을 확인할 수 없습니다" (페이지 로드 시 경고)
- **원인**: 노트북 와이파이가 불안정하거나, Firebase Functions가 일시적으로 응답하지 않음.
- **대처**: 촬영 자체는 계속 가능하다(경고는 사전 안내일 뿐). 와이파이 아이콘을 확인하고, 문제가 지속되면 노트북을 재연결하거나 다른 와이파이 노트북으로 안내.

## 2. "AI가 그리는 중…"에서 계속 멈춰 있음 (콜드스타트)
- **원인**: Cloud Functions 인스턴스가 한동안 요청이 없어 꺼졌다가(콜드스타트), 새 요청에 처음 응답하기까지 수 초~수십 초가 더 걸릴 수 있음. `timeoutSeconds:140`(2026-09-06, 부하테스트 실측 기반으로 120→140초 상향)이라 최대 2분 20초까지는 정상 범위. 프론트(`src/PosterStudio.tsx`)의 150초 타임아웃이 이보다 조금 더 길게 잡혀 있어, 실제로는 사용자가 최대 150초까지 기다린 뒤에야 오류 문구를 본다.
- **이미 완화돼 있다**(2026-08-30 추가, 배포·검증 완료): `keepWarm` 스케줄러가 **행사 당일
  11월 14일 09:00~18:55(KST)에만** 5분 간격으로 `/health`를 핑해 인스턴스를 데워둔다.
  평상시엔 완전히 비활성이라 비용이 없다.
  - ⚠ 이미 떠 있는 인스턴스에 갑자기 여러 명이 몰리는 **1→N 스케일업 콜드스타트까지는
    못 막는다.**
  - 배포 메모(해결됨): 처음엔 CI 서비스계정에 Cloud Scheduler 권한이 없어 배포가 매번
    실패했는데, `roles/cloudscheduler.admin`을 프로젝트 레벨로 추가해 해결됐다. 지금은
    스케줄 변경도 CI로 그냥 나간다.
- **대처**: 2분(자동 타임아웃) 넘게 멈춰 있으면 자동으로 오류 메시지가 뜬다. 그 전에는 기다리는 것이 정답 — 다시 클릭하면 중복 과금만 발생한다(단, "AI 포스터 만들기" 버튼은 진행 중 비활성화되어 중복 클릭 자체는 막혀 있음).

## 3. 429 오류 — 세 가지 원인이 있다
**⚠️ 아래 "여러 부스에서 요청이 몰려 있습니다" 문구는 예전(2026-08-29 이전, 인스턴스별 메모리 카운터) 서술이 여기 남아있던 걸 2026-09-01에 정정한 것이다 — "이 노트북만" 문제가 아니라 원인별로 범위가 다르다:**
### "지금 여러 부스에서 요청이 몰려 있습니다" — 전역 한도

- **대처**: 몇 분 기다렸다 다시 시도하라고 안내한다.
- **범위**: 🔴 **모든 부스가 동시에 영향받는다.** 한 노트북에서 떴으면 다른 노트북도 곧 본다.
- **회복**: 10분 단위 고정 윈도우라 **최대 10분 가까이** 걸릴 수 있다(1~2분이 아니다).
- **자주 뜨면 팀장에게 즉시 보고.** `RATE_LIMIT_MAX` 상향은 코드 수정 + 재배포가 필요하고
  **현장에서 즉시 못 바꾼다.**
- 원리: `functions/index.js`의 `rateLimit`이 Firestore에 **전역 카운터 하나로**(인스턴스·노트북
  구분 없이) 최근 10분 요청 수를 세고 `RATE_LIMIT_MAX`(현재 150)를 넘으면 낸다.
### "이 네트워크에서 요청이 너무 많이 몰렸습니다" — IP별 한도

- **대처**: 몇 분 후 재시도. 반복되면 **그 노트북들이 한 와이파이에 몰려 있는지부터 확인**한다.
- **범위**: 같은 공인 IP를 쓰는 노트북들만. 다른 IP 그룹은 정상이다.
- 원리: 같은 공인 IP에서 10분간 `IP_RATE_LIMIT_MAX`(현재 50)를 넘으면 뜬다. 전역 한도보다
  **먼저 뜰 수도 있다.** 50 = 전역 한도(150) ÷ 공인 IP 3개 — 한 IP가 폭주해도 나머지
  두 그룹은 계속 된다("행사 전 필수 체크리스트 ②" 참고).
- **"이 사진으로는 생성 횟수를 모두 사용했어요" (사진별 한도)**: 같은 사진(바이트 단위로 동일)으로 이미 최초생성+재생성(2회)을 다 썼다는 뜻 — "1인당 1회 재생성" 정책이 서버에서도 강제된다(새로고침해도 우회 안 됨). 이건 그 학생 한 명에게만 영향을 준다. **대처**: 정상 동작이다 — 다시 촬영하면 새 사진으로 카운트가 초기화된다. 2026-10-16부터 **실패한 생성은 이 2회에 세지 않는다**(화면도 성공만 세고, 서버도 실패 응답 직전에 그 사진 카운터를 하나 되돌린다).
### "오늘의 생성 한도에 도달했습니다" — 하루 총량 상한

- **대처**: 🔴 **팀장·대표에게 즉시 보고.** 현장에서 풀 방법이 없다.
- **재부팅해도 안 풀린다** — 다음 KST 날짜로 넘어가야 초기화된다.
- 원리: `dailyBudgetCap`이 KST 하루 요청 수를 세고 `DAILY_BUDGET_MAX`(현재 4000,
  약 $200어치)를 넘으면 낸다. 어떤 트래픽 패턴이든 하루 지출이 이 값을 못 넘게 하는
  물리적 안전장치다(2026-09-01 신설). 정상 사용으로 다 채웠다면 그 자체가
  "예산 목표치 도달"이라는 뜻이다.

### 부스 코드는 쓰지 않는다 — 진짜 생성을 막는 것은 한도뿐 (2026-10-23 Bumm님 확정)
- 행사 날에도 링크만 있으면 주소를 아는 누구나 «이 사진으로 포스터 만들기»로 진짜 생성을 할 수 있다(라이브는 두 단추). 막는 것은 서버 한도 네 가지뿐이다:
  **10분 150건(전체) · 10분 50건(공인 IP 하나) · 사진 한 장당 2회 · 하루 4,000건(KST)** — 하루 최대 약 **$200**(4,000건 × $0.05). 이 값들은 `functions/index.js`에 있다.
  한도에 닿으면 위 세 가지 429 안내가 뜬다. 하루 4,000건에 닿으면 그날은 행사 부스도 못 만든다 — 바로 팀장·Bumm님께 알린다.

## 4. AI 생성이 실패함 — «포스터를 만들지 못했어요» 창 (2026-10-16부터)
- 실패하면 빈 그라데이션 포스터로 넘어가지 않고, 실패 종류에 맞는 단추 두 개가 있는 창이 뜬다. 문구는 한 줄로 짧다(2026-10-17 Bumm님). 서버가 준 원인 문구는 화면에 보이지 않고, 노트북 크롬의 개발자 도구 콘솔에 «[포스터 생성 실패]»로 남는다.

  | 창에 보이는 것 | 할 일 |
  |---|---|
  | «그림을 다 그리지 못했어요»(시간 초과·연결 불안정·알 수 없음) | «다시 만들기». 같은 사진으로 3번 실패하면 «다시 찍기»로 안내한다 |
  | «지금 만드는 사람이 많아요» · «AI가 바빠요» | 15~20초 세고 «다시 만들기»가 켜진다. 자주 뜨면 §3 |
  | «내용을 바꾸거나 다시 찍어 볼까요 ?»(안전 기준) | «제목 · 문구 고치기»(1단계로)로 제목 · 문구를 바꾸거나 «다시 찍기». 사진 · 입력을 그대로 두고 다시 누르면 서버로 보내지 않고 같은 안내가 다시 뜬다(10/26). 같은 요청을 되풀이하는 단추는 없다 — 안전 기준을 피해 가는 방법을 아이에게 알려 주지 않는다 |
  | «이 사진으로는 더 만들 수 없어요» · «여러 번 만들지 못했어요» | «다시 찍기» 또는 «처음으로» |
  | «인터넷 연결이 끊겼어요» | 그 노트북을 다른 와이파이·핫스팟으로 바꾼다. 연결이 돌아오면(5초마다 확인) «다시 만들기»가 켜진다. 사진은 그대로 있다 |
  | «지금은 만들 수 없어요» | 하루 예산·크레딧·키·운영 시간 문제다. 현장에서 못 푼다 — 담당자(대표/장학사)에게 즉시 연락 |
  | «부스 코드를 넣어 주세요» 창 | **쓰지 않음(10/23 — 이 창은 뜨지 않아야 한다. 뜨면 누가 서버 스위치를 켠 것이니 바로 팀장에게).** 예전 설명: 부스 코드가 켜졌는데 이 노트북에 코드가 없거나 틀렸다. 비공개 별지의 코드를 넣으면 확인 뒤 같은 사진으로 다시 만든다. «취소»(와 Esc)는 행사 기기가 아닌 곳을 위한 것이라 탭을 닫고, 브라우저가 닫기를 막으면(사람이 연 탭) 0.3초 뒤 처음 화면으로 돌아간다 — 찍은 사진은 버려진다 |
- 실패는 «사진당 2회»에 세지 않는다(§3).

## 4-2. 인터넷이나 AI가 계속 안 될 때 — Windows 설치판으로 (2026-10-27)
- **언제**: 다른 와이파이 · 핫스팟으로 바꿔도 «인터넷 연결이 끊겼어요»가 계속되거나, «지금은 만들 수 없어요»처럼 현장에서 못 푸는 안내가 뜰 때. 기술 담당이 판단한다.
- **바꾸기**:
  1. 바탕화면 «Poster Studio» 아이콘(검은 영화 슬레이트)을 두 번 누른다. 머리글에 «설치판 · AI 없이 사진 그대로»가 보이면 설치판이다.
  2. 순서는 같다. 영화 준비 → 카메라 켜기(또는 «사진 불러오기») → «이 사진으로 포스터 만들기» → 로딩 화면(장면 둘 · 승인된 대기 영상, 20초쯤) → 찍은 사진 그대로 8종 → «이 포스터로 출력하기» → 인쇄 미리보기 → «인쇄하기» → Windows 인쇄 창에서 포토프린터 · 4×6.
  - AI 그림이 아니다. 인터넷이 없어도 된다(서버 요청 0).
- **돌아오기**: 크롬에서 poster.edutogether.kr을 새로 열었을 때 «AI 서버 연결을 확인할 수 없습니다»가 안 뜨면, 설치판을 닫고 크롬으로 돌아온다.
- **준비**: 설치판은 행사 전에 노트북마다 미리 설치해 둔다.
  1. `Poster Studio Setup.exe`(받는 주소 https://poster.edutogether.kr/download/PosterStudio-Setup.exe)를 두 번 누른다. 서명 없는 설치 파일이라 인터넷에서 받은 파일이면
     SmartScreen «Windows의 PC 보호» 창이 뜬다 — «추가 정보» → «실행».
     🟠 현장 주소는 poster.edutogether.kr 하나이고, USB 배포 · 파일 출처 표시를 지우는 방식은 쓰지 않는다(10/27 Bumm님 방침, 팀장 전달). 경고가 떠도 정상이다 — 서명 · Store는 하지 않고 EXE 그대로 낸다(10/27 Bumm님 A안). 매뉴얼 3쪽에 실제 창 두 장(처음 창 · «추가 정보» 뒤)이 있다.
  2. 설치 범위는 «모든 사용자»(기본)로 두고 «다음» → 위치 그대로 «설치». 관리자 승인 창이 뜨면 «예». 권한이 없으면 «나만»으로 설치해도 된다.
     설치하는 동안 화면 아래 목록에 설치 위치와 하는 일(파일 복사 · 바로 가기 생성)이 한 줄씩 나온다. 예전 판이 깔린 노트북은 그대로 덮어쓴다.
  3. 끝나면 설치판이 바로 열린다. 바탕화면 «Poster Studio»와 시작 메뉴 «InKY Film Festival» 폴더가 생긴다.
  - 지우기: 설정 › 앱 › 설치된 앱 › «Poster Studio» › 제거, 또는 시작 메뉴 «InKY Film Festival» › «Uninstall Poster Studio».
  - 교육청 노트북 관리가 설치를 막는지, 관리자 승인 창이 어떻게 뜨는지는 11/12 장비 시험에서 본다(미검증 — 개발 PC는 승인 창 없이 올라가는 설정이다).
- 설치판 카메라가 안 켜지면: Windows 설정 › 개인 정보 및 보안 › 카메라 › «데스크톱 앱이 카메라에 액세스하도록 허용». 크롬이 카메라를 쓰고 있으면 크롬을 닫는다.
- 설치판 «PC에 저장»은 아이 얼굴 · 이름이 든 PNG를 노트북에 남긴다(12/31까지 보관 후 장학사가 삭제 — 웹의 PNG 저장과 같다). 꼭 필요할 때만 쓴다.

- **원인**: 거의 발생하지 않음(브라우저가 촬영본을 자동으로 1024px로 축소해 보냄). 브라우저 확장 프로그램 등이 개입했을 가능성.

## 6. 프린터가 인쇄를 안 함
- 이 문서 범위 밖(앱 문제 아님) — 프린터 전원/용지/드라이버 확인, 필요시 예비 프린터로 교체.
- 🔴 **전원(멀티탭)부터 확인할 것.** 배터리만으로는 대당 **30장**이 한계(충전 90분)인데,
  **충전하면서 인쇄하면 그 제약이 사라진다**(2026-09-11 현장 확인). 즉 **플러그가 빠져 있으면
  그 프린터는 곧 멈춘다.** 대수·인화지·대기열 계산은 [`printer-capacity.md`](printer-capacity.md).
- **프린터가 밀려도 앱은 계속 쓸 수 있다** — 노트북과 프린터는 분리돼 있으니, 인쇄 대기 중에도
  다음 아이가 촬영·생성을 시작하게 한다.

## 7. 부스토큰(BOOTH_TOKEN) 유출 시 교체 절차
부스토큰은 정적 사이트(`public/constants.js` — ES모듈 전환 전엔 `public/app.js`였음, 2026-08-30 이동)에 값이 그대로 노출되므로 "진짜 비밀"이 아니다 — 소스를 안 보는 자동화 스크립트를 막는 최소 문지기일 뿐이다. 그래도 값을 바꿔야 할 상황(예: 저장소가 예상 밖으로 알려짐, 남용 정황 발견)이 생기면 **아래 순서를 반드시 지킬 것** — 순서가 틀리면 부스 전체가 일시적으로 401로 막힌다.

1. 새 무작위 토큰 생성: `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"`
2. Firebase Secret Manager에 새 값 등록: `printf '<새토큰>' | firebase functions:secrets:set BOOTH_TOKEN --project inky-poster-studio --data-file -`
3. `public/constants.js`의 `BOOTH_TOKEN` 상수를 **같은 값**으로 수정
4. 커밋 후 `master`에 push — CI가 `test` → `deploy-functions`(새 시크릿 반영) → `deploy-hosting`(새 constants.js 반영) 순서로 자동 배포한다. **2·3번을 같은 커밋에 같이 넣을 것** — 하나만 먼저 나가면 그 사이에 401이 뜬다.
5. 배포 완료 후 실제로 `/generate`가 새 토큰으로 정상 응답하는지 확인(CI의 "부스토큰 스모크테스트" 단계가 자동으로 확인하고, 실패하면 파이프라인이 실패로 표시된다).

## 8. 배포가 나갔는데 라이브가 깨졌을 때 (롤백)
2026-10-01 현재 조직 규칙에 맞춘 절차다. 이전 문서의 콘솔·수동 CLI 롤백 안내는 사용하지 않는다.

1. 공통 인계 문서에 적힌 직전 정상 프리즈 태그와 배포 커밋을 확인한다.
2. 작업 가지에서 문제가 된 변경을 `git revert`하고 PR을 만든다. `reset --hard`·강제 푸시·master 직접 푸시는 하지 않는다.
3. 프론트와 Functions 검사 후 정해진 승인 경로로 병합하여 기존 CI가 두 서비스를 다시 배포하게 한다.
4. 해당 커밋의 CI 성공과 두 Hosting 주소의 응답·번들을 확인한다. 실제 `/generate` 호출은 비용이 발생하므로 별도 지시 없이 검사하지 않는다.

Hosting과 Functions를 콘솔에서 직접 바꾸거나 수동 `firebase deploy`로 우회하지 않는다. 되돌린 뒤 공통 인계 문서에 커밋과 CI 결과를 남긴다.
GitHub가 정지돼 CI가 돌지 않을 때만 예외로 §9 절차를 쓴다.

## 9. GitHub 정지 중 로컬 배포 (2026-10-15 Bumm님 승인, 팀장 전달)
GitHub가 정지돼 push·CI가 안 될 때만 쓴다. 매번 팀장을 거친 Bumm님 배포 승인이 있어야 한다. 정상일 때는 §8까지의 CI 경로다.
2026-10-15에 이 절차로 master `8d752d4`를 배포했다(기록은 `_docs/CHANGELOG.md`와 `_docs/intents/2026-10-15-local-deploy-github-suspended/`).

1. **무엇이 나가는지 본다.** 기준(`<라이브 커밋>`)은 **지금 라이브에 나가 있는 커밋**이다 — 공통 인계 문서(`_docs/ops/HANDOFF_CURRENT.md`) 맨 위
   «라이브는 …»에 적힌 것. 🟠 이 절차로 한 번 배포한 뒤로는 `origin/master`가 아니다(2026-10-15 로컬 배포 뒤 라이브는 `8d752d4`,
   `origin/master`는 그보다 56커밋 앞의 `a658d89` — `origin/master`를 기준으로 잡으면 3번 대조에서 멈춘다. 2026-10-17 점검에서 발견).
   GitHub가 정상이고 CI로만 배포해 왔다면 `origin/master`와 같다.
   - 전체: `git diff --stat <라이브 커밋> master`
   - functions: `git diff --stat <라이브 커밋> master -- functions/`. 비어 있으면 hosting만 낸다.
2. **LF 사본을 만든다.** 이 컴퓨터의 체크아웃은 CRLF(`core.autocrlf=true`)라 그대로 빌드하면 CI(LF)와 다른 파일이 나간다.
   ```bash
   git -c core.autocrlf=false worktree add --detach .cache/deploy-<날짜>/base <라이브 커밋>
   git -c core.autocrlf=false worktree add --detach .cache/deploy-<날짜>/master master
   ```
3. **이 컴퓨터의 빌드가 CI를 재현하는지 본다.** `base`에서 `npm ci && npm run build`를 하고, 라이브와 바이트 대조한다.
   - 명령: `node scripts/verify/dist-vs-live.mjs ../base/dist https://poster-studio.web.app`
   - 전부 같아야 다음으로 간다. 다르면 기준 커밋이 지금 라이브가 아니거나 빌드 환경이 다르다 — 멈추고 팀장에게 보고한다.
   - 2026-10-17 점검: `8d752d4` LF 빌드가 두 주소 모두와 323개 파일 바이트까지 같았다.
4. **CI 검사를 `master` 사본에서 전부 돌린다.** 하나라도 종료코드가 0이 아니면 멈춘다.
   - functions: `npm ci` · `npm run lint` · `npm test`
   - 루트: `npm ci` · `npm run lint` · `npm run typecheck` · `npm run fonts:check` · `npm test` · `npm run verify:selftest` · `npm run build`
   - dist 점검: `node scripts/ci/run-workflow-step.mjs "dist에 나가면 안 되는 것이 없는지"`(CI 단계의 명령을 워크플로 파일에서 꺼내 그대로 실행한다)
   - 대기 영상: `node scripts/verify/waiting-videos-live.mjs`
5. **배포 도구는 CI와 같은 잠금 판을 쓴다.**
   - 설치: `cd tools/deploy && npm ci --ignore-scripts --no-audit --no-fund`
   - 확인: `tools/deploy/node_modules/.bin/firebase --version`이 `15.32.1`이어야 한다.
   - 로그인한 계정이 `inky-poster-studio`에 접근되는지 `firebase projects:list`로 본다.
6. **되돌릴 자리를 먼저 만든다.** 지금 라이브 판을 30일짜리 채널에 복제하고, 그 채널이 `base` 빌드와 같은지 대조한다.
   ```bash
   firebase hosting:channel:list --site poster-studio --project inky-poster-studio          # 지금 라이브 판 번호를 적어 둔다
   firebase hosting:channel:create rollback-<날짜> --site poster-studio --expires 30d --project inky-poster-studio
   firebase hosting:clone poster-studio:live poster-studio:rollback-<날짜> --project inky-poster-studio
   node scripts/verify/dist-vs-live.mjs ../base/dist <채널 주소>
   ```
   - functions도 낼 때는 지금 라이브 함수의 지문을 적어 둔다: `firebase functions:list --project inky-poster-studio --json`(`posterStudio`·`keepWarm`·`cleanupOldCountersSchedule`의 해시).
     되돌릴 곳은 `base` 사본(지금 라이브와 같은 커밋)이다.
   - 이미 만든 되돌림 채널이 아직 살아 있고 `base` 빌드와 같으면 새로 만들지 않고 그것을 쓴다(`rollback-20261016-night`는 11/15까지 — 10/17 대조 323개 같음).
   - 2026-10-17 연습: 하루짜리 채널 `rehearsal-1017`에 새 판(미리보기 채널)을 `hosting:clone`으로 올렸다가 되돌림 채널을 다시 `hosting:clone`해
     되돌렸다 — 두 번 다 `dist-vs-live.mjs`로 바이트까지 같았다(300개 · 323개). 9번의 hosting 되돌리기와 같은 명령 꼴이다. 라이브는 건드리지 않았다.
     함수 지문은 그날 `posterStudio` `b327ed39…` · `keepWarm` · `cleanupOldCountersSchedule` `e0f59577…`였다.
7. **배포한다**(`master` 사본에서, CI와 같은 순서).
   - functions가 바뀌었으면 먼저 `firebase deploy --only functions --project inky-poster-studio --non-interactive`를 낸다.
     그다음 `node scripts/ci/run-workflow-step.mjs "부스토큰 스모크테스트 (배포 직후 실제 인증 확인)"`가 통과해야 hosting으로 간다.
     (부스 코드는 쓰지 않는다 — 10/23 확정. 아래 한 줄은 다시 켤 때를 위해 남겨 둔다.) 부스 코드 스위치가 켜졌으면 이 단계는 `BOOTH_CODE_REQUIRED=true`와 `BOOTH_CODE`(값은 비공개 운영 문서)를 환경변수로 넣고 돌린다 —
     «코드 없이 403 booth_code»와 «코드를 실어 400»을 둘 다 본다(2026-10-17). 안 넣으면 403으로 실패하는 것이 맞다.
   - 🔴 **부스 코드 스위치를 켰다면(지금은 쓰지 않음 — 10/23 확정, 절차만 남겨 둠) 그 뒤로는 functions를 그냥 내지 않는다.** CI는 배포할 때마다 «부스 코드 설정» 단계에서 환경 파일을 새로 만들어 넣는다.
     그 파일 없이 내면 켜 둔 스위치가 빠질 수 있다. 비공개 운영 문서의 절차로 같은 파일을 먼저 만들거나, 멈추고 팀장에게 보고한다.
   - hosting: `firebase deploy --only hosting:poster-studio --project inky-poster-studio --non-interactive -m "로컬 배포 <커밋>"`
   - `firebase`는 5번의 `tools/deploy/node_modules/.bin/firebase`다.
8. **배포 직후 CI와 같은 확인을 한다.**
   - 두 주소 바이트 대조:
     - `node scripts/verify/dist-vs-live.mjs dist https://poster.edutogether.kr`
     - `node scripts/verify/dist-vs-live.mjs dist https://poster-studio.web.app`
