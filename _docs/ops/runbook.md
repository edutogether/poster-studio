# 운영 런북 (행사 당일 장애 대응)

부스 진행자가 노트북 앞에서 바로 참고할 수 있도록, 흔히 발생할 수 있는 문제와 대처법을 정리한다.

## ⚠️ 행사 전 필수 체크리스트 (2026-11-14 전에 반드시 확인)
### ① OpenAI 월 지출 하드리밋을 **$10 → $200**으로 올린다

- 지금 $10인 이유: 2026-08-29 개발·테스트 기간에 걸어둔 값이다.
- 안 올리면: 1장당 약 $0.04이므로 **약 250장, 오전 중에 부스 전체의 AI 생성이 멈춘다.**
- 어디서: platform.openai.com → 결제 → 하드리밋.

### ② 노트북을 공인 IP에 고르게 붙인다

- **노트북 3대, 공인 IP 3대** — 대략 IP당 1대다(2026-09-09 대표 확정).
- 왜 고르게: `IP_RATE_LIMIT_MAX=50`(전역 150 ÷ IP 3개)이라, **한 IP에 몰리면 그 그룹만
  정상 사용으로도 50건에 먼저 닿아** 불필요한 429가 난다.
- 현장에서: 어느 노트북이 어느 와이파이를 쓰는지 확인해 대체로 나뉘어 있으면 된다.
- ⚠ 예전 문서에 있던 **"노트북 20대를 7/7/6으로"는 배치 계획이 아니다** — 부하 테스트
  목표치였다. 실제 배치는 위 3대다.

## 1. "AI 서버 연결을 확인할 수 없습니다" (페이지 로드 시 경고)
- **원인**: 노트북 와이파이가 불안정하거나, Firebase Functions가 일시적으로 응답하지 않음.
- **대처**: 촬영 자체는 계속 가능하다(경고는 사전 안내일 뿐). 와이파이 아이콘을 확인하고, 문제가 지속되면 노트북을 재연결하거나 다른 와이파이 노트북으로 안내.

## 2. "AI가 그리는 중…"에서 계속 멈춰 있음 (콜드스타트)
- **원인**: Cloud Functions 인스턴스가 한동안 요청이 없어 꺼졌다가(콜드스타트), 새 요청에 처음 응답하기까지 수 초~수십 초가 더 걸릴 수 있음. `timeoutSeconds:140`(2026-09-06, 부하테스트 실측 기반으로 120→140초 상향)이라 최대 2분 20초까지는 정상 범위. 프론트(`public/api.js`)의 150초 타임아웃이 이보다 조금 더 길게 잡혀 있어, 실제로는 사용자가 최대 150초까지 기다린 뒤에야 오류 문구를 본다.
- **이미 완화돼 있다**(2026-08-30 추가, 배포·검증 완료): `keepWarm` 스케줄러가 **행사 당일
  11월 14일 09:00~18:55(KST)에만** 5분 간격으로 `/health`를 핑해 인스턴스를 데워둔다.
  평상시엔 완전히 비활성이라 비용이 없다.
  - ⚠ 이미 떠 있는 인스턴스에 갑자기 여러 명이 몰리는 **1→N 스케일업 콜드스타트까지는
    못 막는다.**
  - 배포 메모(해결됨): 처음엔 CI 서비스계정에 Cloud Scheduler 권한이 없어 배포가 매번
    실패했는데, `roles/cloudscheduler.admin`을 프로젝트 레벨로 추가해 해결됐다. 지금은
    스케줄 변경도 CI로 그냥 나간다.
- **대처**: 2분(자동 타임아웃) 넘게 멈춰 있으면 자동으로 오류 메시지가 뜬다. 그 전에는 기다리는 것이 정답 — 다시 클릭하면 중복 과금만 발생한다(단, "AI 포스터 만들기" 버튼은 진행 중 비활성화되어 중복 클릭 자체는 막혀 있음).

## 3. 429 오류 — 세 가지 원인이 있다
**⚠️ 아래 "여러 부스에서 요청이 몰려 있습니다" 문구는 예전(2026-08-29 이전, 인스턴스별 메모리 카운터) 서술이 여기 남아있던 걸 2026-09-01에 정정한 것이다 — "이 노트북만" 문제가 아니라 원인별로 범위가 다르다:**
### "지금 여러 부스에서 요청이 몰려 있습니다" — 전역 한도

- **대처**: 몇 분 기다렸다 다시 시도하라고 안내한다.
- **범위**: 🔴 **모든 부스가 동시에 영향받는다.** 한 노트북에서 떴으면 다른 노트북도 곧 본다.
- **회복**: 10분 단위 고정 윈도우라 **최대 10분 가까이** 걸릴 수 있다(1~2분이 아니다).
- **자주 뜨면 팀장에게 즉시 보고.** `RATE_LIMIT_MAX` 상향은 코드 수정 + 재배포가 필요하고
  **현장에서 즉시 못 바꾼다.**
- 원리: `functions/index.js`의 `rateLimit`이 Firestore에 **전역 카운터 하나로**(인스턴스·노트북
  구분 없이) 최근 10분 요청 수를 세고 `RATE_LIMIT_MAX`(현재 150)를 넘으면 낸다.
### "이 네트워크에서 요청이 너무 많이 몰렸습니다" — IP별 한도

- **대처**: 몇 분 후 재시도. 반복되면 **그 노트북들이 한 와이파이에 몰려 있는지부터 확인**한다.
- **범위**: 같은 공인 IP를 쓰는 노트북들만. 다른 IP 그룹은 정상이다.
- 원리: 같은 공인 IP에서 10분간 `IP_RATE_LIMIT_MAX`(현재 50)를 넘으면 뜬다. 전역 한도보다
  **먼저 뜰 수도 있다.** 50 = 전역 한도(150) ÷ 공인 IP 3개 — 한 IP가 폭주해도 나머지
  두 그룹은 계속 된다("행사 전 필수 체크리스트 ②" 참고).
- **"이 사진으로는 생성 횟수를 모두 사용했어요" (사진별 한도)**: 같은 사진(바이트 단위로 동일)으로 이미 최초생성+재생성(2회)을 다 썼다는 뜻 — "1인당 1회 재생성" 정책이 서버에서도 강제된다(새로고침해도 우회 안 됨). 이건 그 학생 한 명에게만 영향을 준다. **대처**: 정상 동작이다 — 다시 촬영하면 새 사진으로 카운트가 초기화된다.
### "오늘의 생성 한도에 도달했습니다" — 하루 총량 상한

- **대처**: 🔴 **팀장·대표에게 즉시 보고.** 현장에서 풀 방법이 없다.
- **재부팅해도 안 풀린다** — 다음 KST 날짜로 넘어가야 초기화된다.
- 원리: `dailyBudgetCap`이 KST 하루 요청 수를 세고 `DAILY_BUDGET_MAX`(현재 4000,
  약 $160어치)를 넘으면 낸다. 어떤 트래픽 패턴이든 하루 지출이 이 값을 못 넘게 하는
  물리적 안전장치다(2026-09-01 신설). 정상 사용으로 다 채웠다면 그 자체가
  "예산 목표치 도달"이라는 뜻이다.

## 4. AI 생성이 계속 실패함 (크레딧 소진·API 장애 등)
- **원인**: OpenAI 쪽 크레딧 소진, 서비스 장애, 또는 노트북 인터넷 자체가 끊김.
- **대처**:
  1. 화면에 뜨는 오류 문구를 확인 — "크레딧 잔액 부족", "API 키가 올바르지 않습니다" 등 구체적인 원인이 표시된다.
  2. 여러 번 실패하면 **"🎨 AI 없이 기본 버전으로 계속하기"** 버튼이 나타난다. 이걸 누르면 AI 그림 없이(단색 그라디언트 배경) 같은 레이아웃으로 포스터를 만들어 인쇄까지는 계속할 수 있다 — 완전히 부스를 멈추지 않기 위한 최소한의 대안.
  3. 근본 원인(크레딧/API 키)은 부스 진행자가 고칠 수 없다 — 담당자(대표/장학사)에게 즉시 연락.

## 5. 사진 업로드가 "사진 파일이 너무 큽니다" 오류
- **원인**: 거의 발생하지 않음(브라우저가 촬영본을 자동으로 1024px로 축소해 보냄). 브라우저 확장 프로그램 등이 개입했을 가능성.
- **대처**: 다시 촬영 후 재시도. 반복되면 다른 노트북으로 안내.

## 6. 프린터가 인쇄를 안 함
- 이 문서 범위 밖(앱 문제 아님) — 프린터 전원/용지/드라이버 확인, 필요시 예비 프린터로 교체.
- 🔴 **배터리부터 의심할 것.** 완충 연속 **30장**이 스펙이고 충전에 **90분**이 걸린다 —
  부스당 330장을 뽑아야 하므로 **행사 중 반드시 바닥난다.** 대수·배터리·인화지·대기열 계산은
  [`printer-capacity.md`](printer-capacity.md).
- **프린터가 밀려도 앱은 계속 쓸 수 있다** — 노트북과 프린터는 분리돼 있으니, 인쇄 대기 중에도
  다음 아이가 촬영·생성을 시작하게 한다.

## 7. 부스토큰(BOOTH_TOKEN) 유출 시 교체 절차
부스토큰은 정적 사이트(`public/constants.js` — ES모듈 전환 전엔 `public/app.js`였음, 2026-08-30 이동)에 값이 그대로 노출되므로 "진짜 비밀"이 아니다 — 소스를 안 보는 자동화 스크립트를 막는 최소 문지기일 뿐이다. 그래도 값을 바꿔야 할 상황(예: 저장소가 예상 밖으로 알려짐, 남용 정황 발견)이 생기면 **아래 순서를 반드시 지킬 것** — 순서가 틀리면 부스 전체가 일시적으로 401로 막힌다.

1. 새 무작위 토큰 생성: `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"`
2. Firebase Secret Manager에 새 값 등록: `printf '<새토큰>' | firebase functions:secrets:set BOOTH_TOKEN --project inky-poster-studio --data-file -`
3. `public/constants.js`의 `BOOTH_TOKEN` 상수를 **같은 값**으로 수정
4. 커밋 후 `master`에 push — CI가 `test` → `deploy-functions`(새 시크릿 반영) → `deploy-hosting`(새 constants.js 반영) 순서로 자동 배포한다. **2·3번을 같은 커밋에 같이 넣을 것** — 하나만 먼저 나가면 그 사이에 401이 뜬다.
5. 배포 완료 후 실제로 `/generate`가 새 토큰으로 정상 응답하는지 확인(CI의 "부스토큰 스모크테스트" 단계가 자동으로 확인하고, 실패하면 파이프라인이 실패로 표시된다).

## 8. 배포가 나갔는데 라이브가 깨졌을 때 (롤백)
6차 감사 발견(2026-09-01): 이 저장소엔 "런타임 장애" 대응만 있고 "배포 자체가 문제였을 때" 절차가 없었다 — Hosting과 Functions는 롤백 방법이 다르므로 구분해서 기록한다.

**Firebase Hosting(정적 프론트엔드)이 깨졌을 때**
- 가장 빠른 방법: Firebase 콘솔 → Hosting → `poster-studio` 사이트 → 배포 이력(Release history)에서 직전 정상 버전 옆의 "되돌리기(Rollback)" 클릭 — 즉시 적용된다(재빌드/재배포 불필요).
- CLI로도 가능: `firebase hosting:rollback --project inky-poster-studio` (대화형으로 최근 배포 목록을 보여주고 고른 버전으로 되돌림 — CI가 아니라 로컬에서 소유자급 계정으로 실행할 것).

**Firebase Functions(백엔드)가 깨졌을 때**
- Cloud Functions는 콘솔에 원클릭 롤백이 없다 — **문제가 된 커밋 이전의 정상 커밋으로 되돌려 재배포**하는 방식이다.
- `git revert <문제커밋SHA>` (또는 `git checkout <정상커밋SHA> -- functions/`로 해당 커밋 상태만 되돌린 뒤 새 커밋) → `master`에 push해 CI가 정상 배포하게 하거나, 급하면 로컬에서 소유자급 계정(`edutogether2015@gmail.com`)으로 `firebase deploy --only functions --project inky-poster-studio`를 직접 실행(CI를 기다릴 필요 없음 — 이 저장소가 5차 감사 때부터 실제로 써온 방법).
- 롤백 후에는 반드시 `/health`와 실제 `/generate` 한 번으로 라이브 정상 동작을 재확인할 것.
