# 태그 정리 — 옮긴 것 (2026-09-10)

대표 결정으로 프리즈 태그를 정리했다(`COMMON_STANDARDS.md` §23-6).

> "못을 너무 많이 박으면 고정인가? 망침이지 — 오히려 이정표가 정신 사나워진다."

**지우지 않았다. 옮겼다.** 아래 태그들은 `refs/archive/tags/<원래이름>`으로 옮겨서
`git tag`와 GitHub 태그 목록에는 안 보이지만, **커밋은 그대로 살아 있다.**

```bash
git checkout refs/archive/tags/poster-studio-freeze-20260903   # 언제든 돌아갈 수 있다
git show refs/archive/tags/poster-studio-freeze-20260903       # 태그 메시지도 그대로
```

🔴 **새로 클론한 저장소에서는 위 명령이 바로 안 된다.** `refs/archive/*`는 `git clone`·
`git fetch`의 기본 대상이 아니기 때문이다(기본은 `+refs/heads/*:refs/remotes/origin/*`).
**먼저 한 줄 받아온다:**

```bash
git fetch origin 'refs/archive/*:refs/archive/*'
```

**옮긴 태그의 커밋은 전부 `master`의 조상이다**(옮기기 전에 7개 전부 확인함). 즉 태그가
없어도 커밋 해시로 언제든 닿는다 — 아래 표에 해시를 남기는 이유가 그것이다.

## 참고 — 두 리액트 태그의 차이 (둘 다 옮겼지만 같은 것이 아니다)

둘 다 "리액트 전환 직전"처럼 보이지만 **가리키는 시점이 다르고, 전환 직전의 라이브 화면을
담은 것은 하나뿐이다.**

- `pre-react`(`5e43449`, 09-09 **00:35**) — 전환 **작업을 시작하기 전**. 이 커밋은
  `master`와 전환 브랜치의 갈라진 지점(merge-base)이기도 하다.
- `pre-react-merge`(`ab2eb31`, 09-09 **19:33**) — 전환본이 `master`에 머지되기 **직전의
  라이브 상태**.

**그 사이에 커밋 27개가 있고, 그날 대표 지시로 라이브에 나간 화면 변경이 전부 거기 있다** —
앱 이름 변경, 헤더 확대, 개인정보 링크 위치, `privacy.html` 재작성, 캐시 규칙 수정,
개인/단체 스위치, 라벨을 입력칸 옆으로, ※ 안내 영역, 초기화 버튼, 여백 재배분,
폰트 서브셋(첫 로드 3.8MB → 157KB).

즉 **아카이브에서 "전환 직전 화면"을 꺼내 볼 일이 생기면 `pre-react`가 아니라
`pre-react-merge`를 꺼내야 한다.** `pre-react`는 그날 화면 작업 이전이라 전환 직전 상태를
대표하지 못한다.

## 옮기는 절차 (순서를 지킨다)

**푸시가 조용히 실패한 상태에서 태그를 지우면 복구 경로가 그 순간 사라진다.** 그래서
"내가 방금 푸시했다"를 믿지 않고 **서버에 다시 물어본 뒤에** 지운다(`COMMON_STANDARDS.md` §23-6).

```bash
git update-ref refs/archive/tags/<이름> <태그객체>          # 1. 아카이브 ref 생성
git push origin refs/archive/tags/<이름>:refs/archive/tags/<이름>   # 2. 올린다
git ls-remote origin 'refs/archive/*'                      # 3. 🔴 서버에 되물어 확인
git push origin :refs/tags/<이름> && git tag -d <이름>      # 4. 그 다음에 삭제
```

3번에서는 **`<이름>^{}`이 실제 커밋으로 풀리는지**까지 본다 — 주석 태그 객체가 안 올라가
ref만 있는 상태와 구별하기 위해서다. 6개 전부 확인했고 표의 해시와 일치했다.
`refs/archive/tags/poster-studio-freeze-20260909-pre-react-merge`를 실제로 체크아웃해
`public/app.js`의 내용이 읽히는 것까지 확인했다(ref만 있고 객체가 없는 상태가 아님).

이 저장소는 `pre-push` 훅이 없어 **삭제를 막아 줄 것이 없다.** 그래서 이 순서가 특히 중요하다.
