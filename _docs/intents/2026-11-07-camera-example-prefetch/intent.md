# 1단계에 머무는 동안 2단계 예시 영상을 미리 받기

## 문제

Bumm님(11/7, 팀장 전달): «포스터 첫 페이지 들어가면 두 번째 페이지의 영상들도 미리 받아놓으면 안 돼 ? 이름이랑 제목 적고 있을 동안 ? 넘기면 처음에 좀 딜레이되었다 시작되는 게 좀 아쉬운데»

지금은 2단계에 들어와서야 `<video>`에 주소를 넣는다(`src/studio/CameraExample.tsx`). 영상은 혼자 2.9MB · 단체 4.1MB다.

## 원하는 결과

- 1단계에 머무는 동안 지금 고른 모드의 예시 영상을 뒤에서 받아 둔다.
- 2단계로 넘어가면 지연 없이 시작한다. 받기가 끝나기 전에 넘어가도 정상 동작한다.
- 입력 칸 타자와 1단계 화면을 방해하지 않는다.
- 전/후를 같은 조건으로 재서 숫자로 보고한다. 받는 양(휴대폰 데이터 · 저사양 학교 PC 부담)도 숫자로 적는다.

## 영향받는 사용자·시스템

- 웹 첫 화면을 여는 모든 사람(휴대폰 포함) — 2단계로 넘어가지 않아도 영상 값이 나간다.
- 설치판은 파일이 로컬이라 미리 받지 않는다(서버 요청 0 원칙 그대로).

## 제약

- 승인된 영상의 화질 · 길이를 낮추지 않는다. 영상 파일을 바꾸지 않는다.
- 라이브에서 «생성»을 누르지 않는다. 프롬프트 동결 그대로.
- «움직임 줄이기»면 받지 않는다(지금도 영상을 쓰지 않는다).
- 2단계를 떠나면 소리 · 다운로드를 정리하는 지금 동작을 유지한다.
- 배포는 «배포 직전 한 줄» → 팀장 OK 뒤.

## 측정으로 가른 것

지연의 원인은 망에 따라 다르다(라이브 측정, 클릭 → 재생 중앙값).

- 와이파이 10Mbps: 처음 약 0.21~0.50초, 다시 약 0.06초. 파일을 fetch로 다 받아 둔 처음 방문도 0.216초였다 — 대부분이 다운로드가 아니라 **그 브라우저의 첫 재생 준비(약 0.15초)**다.
- 느린 망 1.6Mbps: 처음 약 2.5~5.8초. 대부분 다운로드이고, 영상 비트레이트(약 2.89Mbps)가 망보다 커서 재생 중에도 끊긴다.

## 방식

- fetch로 캐시에 받는 방식을 버렸다. 첫 재생 준비가 그대로 남기 때문이다. blob 주소도 CSP(`media-src` 없음)에 막힌다.
- **2단계에서 쓸 `<video>`를 1단계에 미리 연다**(재생 · 소리 없음). 넘어갈 때 같은 요소가 받던 것을 이어 받으므로 끊기거나 두 번 받지 않는다.
- 첫 시도는 `load`만 기다렸는데, 1단계 장르 포스터가 `load` 뒤에 요청되어 영상과 망을 나눠 썼다(1.6Mbps에서 첫 페이지 약 3초 지연, 5초 만에 넘기면 영상이 끝나는 시각도 약 1.2초 늦음). 그래서 **문서 · 그림 · 글꼴을 다 받은 뒤(늦어도 20초) 시작**한다.
- 데이터 절약 모드(`saveData`) · 움직임 줄이기 · 카메라 켬 · 설치판은 미리 받지 않는다.

## 전/후(같은 빌드 조건 · 로컬 HTTP/2 · 각 2회, 1366×768 · 390×844 3배)

재생 시작은 «다음» 클릭 → 재생까지 ms다.

| 조건 | 방문 | 재생 시작 전 → 후 | 재생 중 멈춤 전 → 후 |
|---|---|---|---|
| 와이파이 10Mbps(8초 머묾) | 처음 | 217~272 → 16~28 | 1회 약 0.2초 → 0 |
| 와이파이 10Mbps | 다시 | 60~69 → 11~17 | 1회 약 0.05초 → 0 |
| CPU 4배 제한 PC(8초) | 처음 | 350~453 → 148~182 | 1회 약 0.2초 → 0 |
| CPU 4배 제한 PC | 다시 | 112~1420 → 49~60 | 1회 0.04~1.3초 → 0 |
| 1.6Mbps(30초) 혼자 | 처음 | 860~874 → 16~27 | 4회 약 7.6초 → 0(끝 15.8초 → 8.3초) |
| 1.6Mbps(30초) 단체 | 처음 | 841~887 → 16~25 | 5회 약 17.4초 → 0(끝 25.6초 → 8.3초) |
| 1.6Mbps(30초) | 다시 | 60~67 → 9~17 | 1회 약 0.05초 → 0 |

## 받는 양 · 부담

| 항목 | 값 |
|---|---|
| 혼자 / 단체 영상 | 2.91MB / 4.12MB |
| 2단계로 가는 사람 | 추가 없음(어차피 받던 양, 클릭 뒤 0) |
| 1단계만 보고 떠나는 사람 | 추가 2.9MB(혼자), 단체를 고르면 그 전에 받은 혼자 몫까지 최대 7.0MB |
| 모드를 바꾸면 | 받던 것을 끊고 새로 받는다(실측 와이파이 6.0MB · CPU 제한 6.9MB) |
| CPU 시간(크롬 전체, 1단계 동안) | 처음 와이파이 8초 머묾 1.3~1.9초 → 1.6~2.5초, CPU 제한 9.7~10.0초 → 9.6~10.7초, 다시 거의 같음 |
| 메모리(크롬 전체) | 처음 약 +100MB(와이파이 699~722 → 797~822MB), 다시 거의 같음 |
| 타자 입력 처리 최대 | 와이파이 24~72 → 24~96ms, 1.6Mbps 24~48 → 24~64ms, 긴 작업 0건 |

## 한계

- 세션은 실제 아이폰을 잴 수 없다. 윈도용 WebKit에서는 1단계에서 멈춘 채 받아 두고(`readyState` 4) 2단계에서 같은 요소로 재생했다. 실제 사파리가 `preload`를 줄이면 효과가 작을 수 있지만, 그때는 예전과 같고 데이터도 더 들지 않는다.
- 숫자는 로컬 서버(HTTP/2)에서 잰 것이다. 배포 뒤 라이브에서 같은 도구로 다시 잰다.
