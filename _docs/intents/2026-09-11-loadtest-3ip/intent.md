# 행사 당일을 실제로 재현하는 부하테스트 설계

## 문제

지금 도구로는 **"행사 당일을 버틴다"고 말할 수 없다.**

- `scripts/loadtest.mjs`는 노트북 **한 대**에서 돈다 = **공인 IP 하나**만 쓴다.
- 서버의 IP별 한도는 **50건/10분**(`IP_RATE_LIMIT_MAX`)이고, 전역은 150건/10분이다.
  **한 대에서 아무리 세게 쏴도 IP 버킷 하나만 소모**하므로, 재는 것은 "여러 대를 버티는가"가
  아니라 "IP 한도가 잘 막는가"가 된다.
- 2026-09-10에 지속(연속) 모드(`--sustain`)를 붙였지만 **이 한계는 그대로다.**

🔴 **전제가 2026-09-11에 바뀌었다 — 기준은 노트북 6대다.**

> *"20대는 할 필요 없다. **행사장 노트북이 6대**니까 6대 기준일 때 가격, 3대 기준일 때 가격
> 정도는 주고 얘기해라."* (대표, 2026-09-11)

**"노트북 20대"는 폐기한다.** 부하 테스트 목표치로 쓰이던 숫자였고, 이 문서 어디에도 기준으로
남기지 않는다 — 남겨두면 다음 사람이 또 그걸로 읽는다.

| | 기준 | 비교용 |
|---|---|---|
| 노트북 | **6대**(2026-09-11 대표) | 3대 |
| 공인 IP | **3개**(대여 와이파이 2 + 핫스팟 1) — IP당 **2대** | 3개, IP당 1대 |

⚠ **`.claude/rules/app.md`는 아직 "노트북 3대"(2026-09-09 확정)로 적혀 있다.** 6대가 확정이면
그 문서도 고쳐야 하고, **프린터 2대 상시 운용이 6대를 받아낼 수 있는지**도 같이 확인해야 한다
(생성은 서버가 하지만 인쇄는 프린터가 병목이다). → 미결 질문 6번.

## 원하는 결과

**서로 다른 공인 IP 3곳에서 동시에 쏘는 테스트**를 돌려, 아래 셋을 숫자로 답할 수 있게 된다.

1. **행사 당일 부하에서 응답시간이 서버 타임아웃(120초)보다 30초 이상 여유가 있는가**
2. **한도에 걸리지 않는가** — 정상 사용 모양에서 429가 0건인가
3. **한도를 넘겼을 때 제대로 거부하고 회복하는가** — 429가 나온 뒤 다음 버킷에서 정상화되는가

### 세 갈래로 나눈다 — 같은 실행에서 볼 수 없다

| | 무엇을 재나 | 부하 모양 | 429 기대 |
|---|---|---|---|
| **A. 6대 재현** | 그날 실제 부하 | 노트북 **6대**(IP 3개 × 2대), 아이 한 명당 체험 1주기 | **0건이어야 정상** |
| **B. 3대 비교** | 절반 규모 | 노트북 **3대**(IP당 1대), 같은 주기 | **0건이어야 정상** |
| **C. 거부 동작** | 방어 장치 | 한도를 일부러 초과 | **나오는 것이 정상** |

**A·B와 C를 같은 실행에서 하면 안 된다** — C가 카운터를 태워버려 A·B의 429가 "정상 부하 때문인지
직전 C 때문인지" 구별할 수 없게 된다. 버킷이 10분이므로 **C 이후 최소 10분을 비운다.**

## 영향받는 사용자·시스템

- **실사용자 없음**(행사 전). 다만 **라이브 서버·라이브 카운터**를 쓴다 — 도는 동안 다른 부스가 429가 된다.
- **실비용이 나간다**(OpenAI 이미지 생성). 아래 비용 항목 참고.
- 건드리는 것: `scripts/loadtest.mjs`, 새 워크플로 1개, `functions/`는 **안 건드린다**(측정 대상이라 그대로 둔다).

## 어떻게 IP 3개를 만드나 — 후보와 **실측 결과**

🔴 **추측하지 않고 확인했다.** 3개인 줄 알았는데 하나면 테스트 전체가 무의미해지기 때문이다.

| 후보 | IP가 갈리는가 | 확인 |
|---|---|---|
| **GitHub Actions 병렬 잡 3개** | ✅ **갈린다** | **2026-09-11 실측** — 병렬 잡 3개가 `172.215.217.197` / `20.112.122.49` / `172.174.118.33`. 두 조회처(ipify·AWS)가 같은 값을 줬다. 워크플로: `.github/workflows/egress-ip-check.yml`(수동 실행 전용, 비용 0) |
| 클라우드 VM 3대 | 갈린다(고정 IP 지정 가능) | 미확인 — 계정·과금이 필요해 대표 처리 사항 |
| 노트북 + 모바일 테더링 2개 | 갈릴 것 | 미확인 — 행사장과 가장 비슷하지만 사람이 붙어야 한다 |
| 같은 사무실 기기 여러 대 | ❌ **안 갈린다** | 같은 NAT 뒤라 공인 IP 하나다. **"3대니까 IP 3개"라고 착각하기 쉬운 자리** |

**권고: GitHub Actions.** 무료이고, 재현 가능하고, **IP가 갈리는 것을 이미 확인**했다.

🔴 **러너는 6개가 아니라 3개면 된다.** 행사장은 **공인 IP 3개에 노트북 6대 = IP당 2대**이므로,
**러너 하나가 노트북 2대를 흉내 낸다**(그 러너 안에서 동시 2, 각자 자기 주기로). 서버가 보는 것은
**IP별 요청 흐름**이지 기기 대수가 아니므로 이렇게 하면 IP 묶음이 그대로 재현된다.
러너를 6개 쓰면 오히려 **IP가 6개로 갈려 실제와 달라진다** — 행사장에는 없는 여유가 생긴다.
3대 비교(B)는 러너 3개 × 동시 1이다.

⚠ **한계를 먼저 적는다**: 러너는 데이터센터에서 돌아 **행사장 네트워크(대여 와이파이·핫스팟)보다
회선이 좋다.** 따라서 이 테스트의 응답시간은 **낙관적으로 나온다** — 서버 용량은 검증하지만
**현장 회선 품질은 검증하지 못한다.** 그쪽은 `scripts/badnet.md` 체크리스트가 담당한다.
러너 IP는 매번 달라지고 우리가 고를 수 없지만, **서로 다르다는 성질**만 필요하므로 문제되지 않는다.

## 부하 모양 — 🔴 "N대 동시"와 "N대 사용"은 전혀 다르다

`동시 N건`은 **동시에 N건이 서버에서 처리 중**이라는 뜻이다. 그런데 실제로는 아이가 촬영하고,
입력하고, 결과를 보고, 인쇄한다 — **한 대가 쉬지 않고 생성만 하지 않는다.** 그래서 부하량은
대수가 아니라 **체험 1주기(T)**가 결정한다: `10분당 요청 = 대수 × (10 / T)`.

**체험 1주기는 아직 모른다**(미결 질문 1). 한 숫자에 갇히지 않도록 **2·4·6분 세 경우**를 다 계산한다.

| 대수 | 주기 | 10분당 요청 | IP당(IP 3개) | IP 한도 50 대비 | 전역 150 대비 |
|---|---|---|---|---|---|
| **6대** | 2분 | 30.0 | **10.0** | **20%** | 20% |
| **6대** | 4분 | 15.0 | 5.0 | 10% | 10% |
| **6대** | 6분 | 10.0 | 3.3 | 7% | 7% |
| 3대 | 2분 | 15.0 | 5.0 | 10% | 10% |
| 3대 | 4분 | 7.5 | 2.5 | 5% | 5% |
| 3대 | 6분 | 5.0 | 1.7 | 3% | 3% |

🔴 **결론: 6대에서는 어떤 주기에서도 429가 나지 않는다.** 가장 빡빡한 경우(주기 2분)조차 IP 한도의
**20%**밖에 안 쓴다. **정상 사용으로는 한도를 절대 건드릴 수 없다** — 그래서 **거부 동작(C)은
반드시 별개 실행**이어야 하고, 그때는 일부러 한도를 넘겨야 한다.

**최대 동시 처리 건수는 대수와 같다** — 6대면 서버에서 동시에 도는 것은 최대 6건이다. 한 건이
약 40초이므로 그보다 늘어날 수 없다. (예전 문서의 "20 동시"는 IP당 100건/10분이 되어 한도를 두 배
넘기는 모양이었다 — 그건 성능이 아니라 거부 동작을 재는 것이었다.)

⚠ **재생성을 반영하면 위 값에 `× (1 + 재생성 비율)`을 곱한다.** 사진 한 장당 최대 2회이므로
전원이 한 번씩 다시 누르면 **두 배**다. 그래도 6대·주기 2분에서 IP당 20건 = 한도의 40%로,
여전히 429는 안 난다. 비율은 미결 질문 2번.

## 통과 기준 — 🔴 돌리기 전에 못박는다

결과를 보고 나서 "이 정도면 됐다"고 하지 않기 위해 미리 적는다.

| 항목 | 기준 | 근거 |
|---|---|---|
| p95 응답시간 | **90초 이하** | 서버 타임아웃 120초 − 요구 여유 30초(2026-09-06 대표 요구 기준, `loadtest.mjs`의 `REQUIRED_MARGIN_SEC`) |
| 실패율(429 제외) | **0%** | 생성 실패는 아이가 빈손으로 돌아가는 것이다 |
| 5xx | **0건** | 하나라도 나오면 원인을 밝히기 전까지 통과 아님 |
| 429 (A·B) | **0건** | 정상 사용 모양에서 한도에 걸리면 한도 산정이 틀린 것이다 |
| 429 (C) | **나와야 통과** + 다음 10분 버킷에서 **정상 복구** | 막는 것이 목적이므로 안 나오면 방어가 안 도는 것이다 |
| 임시파일 | C 실행 후 `/tmp` 누수 없음 | 429 경로의 사진 삭제는 2·7·8차 감사에서 **세 번 재발**한 자리다 |

## 비용 — 무엇 × 몇 건 × 단가

단가 **$0.04/건**(OpenAI 이미지 생성 `gpt-image-2`·medium·1024x1536·`VARIANTS=1`, 1요청=1장).
같은 단가로 `DAILY_BUDGET_MAX=4000`을 $160으로 계산해 코드에 박아 둔 값이다.

### 얼마나 오래 돌릴 것인가 — 두 안

**30분 축약**은 10분 버킷을 3개 지나므로 롤오버는 볼 수 있지만 **행사 4시간 30분의 누적 효과**는
못 본다(콜드스타트 반복, 인스턴스 회수, 카운터 누적). **270분 전체 재현**은 그날과 같은 길이다.

| 대수 | 주기 | 30분 축약 | | 270분 전체 재현 | |
|---|---|---|---|---|---|
| | | 요청 | 비용 | 요청 | 비용 |
| **6대** | 2분 | 90 | $3.60 | 810 | **$32.40** |
| **6대** | **4분** | 45 | $1.80 | **405** | **$16.20** |
| **6대** | 6분 | 30 | $1.20 | 270 | $10.80 |
| 3대 | 2분 | 45 | $1.80 | 405 | $16.20 |
| 3대 | 4분 | 22 | $0.88 | 202 | $8.08 |
| 3대 | 6분 | 15 | $0.60 | 135 | $5.40 |

**C(거부 동작)**은 대수와 무관하다 — 한도를 일부러 넘기는 것이라 **하드 상한 400건 = 상한 $16**이고,
**429는 과금되지 않으므로 실제 지출은 성공분(10분당 최대 150건)뿐**이다.

### 권고안과 총액

**A(6대) 270분 전체 재현 + B(3대) 30분 비교 + C(거부 동작)** = 주기 4분 기준
**$16.20 + $0.88 + 최대 $16 = 최대 약 $33**, 429가 과금되지 않으므로 **실제는 $20 안팎**.

⚠ **주기가 2분으로 밝혀지면 A만 $32.40**이 되어 총액이 **$49**까지 오른다. 대표가 *"아까 정도
금액이면 괜찮다"*($25 수준)고 하셨으므로, **주기가 2분이면 A를 270분이 아니라 절반(135분)으로
줄이거나 다시 여쭙는다.** 세션이 임의로 정하지 않는다.

어느 안이든 **하루 예산 `DAILY_BUDGET_MAX=4000`($160)** 안이다.

## 제약

- 🔴 **실행은 대표 승인 뒤에만.** `--confirm` 없이는 도구가 거부한다(종료코드 1).
- 🔴 **행사 당일(2026-11-14)에는 절대 돌리지 않는다.**
- 🔴 **`functions/`의 한도·타임아웃 상수를 테스트를 위해 바꾸지 않는다.** 측정 대상을 고치면 측정이 아니다.
- **부스토큰을 코드·로그에 남기지 않는다** — GitHub Secrets로 넣고 마스킹을 확인한다.
- **A·B와 C 사이에 최소 10분**(버킷 롤오버)을 비운다.
- 결과에는 **"이 테스트가 검증하지 못한 것"**(현장 회선 품질, 프린터 처리량)을 반드시 함께 적는다.

## 미결 질문

1. 🔴 **아이 한 명의 체험 1주기가 몇 분인가?**(촬영 → 입력 → 생성 → 확인 → 인쇄까지) **이걸 모르면
   B의 부하 모양을 만들 수 없다.** 위 계산은 4분 가정이다.
2. **재생성 비율** — 사진 한 장당 최대 2회인데, 몇 %가 재생성을 누를 것으로 볼 것인가. 생성 건수가 그만큼 늘어난다.
3. **C(거부 동작)를 라이브에 돌릴 것인가.** 돌리는 동안 전 부스가 429가 된다. 행사 전이라 실사용자는
   없지만 결정 사항이다.
4. **A(6대)를 30분 축약으로 할 것인가, 270분 전체 재현으로 할 것인가.** 전체 재현만이 그날의
   누적 효과(콜드스타트 반복, 인스턴스 회수)를 본다. **주기가 2분으로 밝혀지면 전체 재현이
   $32.40이라 "아까 정도 금액"을 넘는다** — 그때는 절반으로 줄일지 다시 여쭙는다.
5. **C(거부 동작)까지 하면 총액이 최대 약 $33**(실제는 $20 안팎)이다. 여기까지 승인인가.
6. 🔴 **노트북이 6대로 바뀐 것이 확정인가.** `.claude/rules/app.md`는 아직 **3대**(2026-09-09 확정)로
   적혀 있다. 확정이면 그 문서를 고쳐야 하고, **프린터 2대 상시로 6대를 받아낼 수 있는지**도
   같이 봐야 한다 — 생성은 서버가 하지만 **인쇄는 프린터가 병목**이다.
7. **GitHub Actions로 갈 것인가** — 무료·재현 가능·IP 갈림 확인 완료. 다만 회선이 좋아 응답시간이
   낙관적으로 나온다. 현장과 같은 회선으로 재려면 사람이 기기를 들고 붙어야 한다.

## 하지 않기로 한 것

- **한도를 잠깐 올리고 테스트하기** — 측정 대상을 고치는 것이라 하지 않는다.
- **행사장 실제 와이파이로 사전 테스트** — 대여 회선이 행사 당일에만 있으므로 불가.
- **20 동시(in-flight)를 "정상 부하"로 재기** — 서버 한도가 허용하지 않는 모양이라 C로만 다룬다.
